## Method

- **Data.** Each server holds the books twice, in `books_bare` (no index) and `books_indexed` (indexes `titleFr` on `title.fr` and `internalTitleFr` on `_internal.data.title.fr`), and as many reviews (the row count is in Environment). A book is written by `toDatabase` from a table class with two `@Localized({ fallbackLocale: "en" })` fields, so `_internal` is `{ meta: {}, data: { title: { fr, en }, summary: { fr, en } } }` as the decorators store it; the book also has a declared `title: { fr, en }` object of its own. Titles are a permutation of the ids, so the title order is not the id order. Every row is inserted through the module, never by SQL.
- **Queries.** Each question is asked in each form the interface offers: `path` hands `orderBy` or `lookup` the dotted path (or the index name on `books_indexed`), `keys` chains `key()` in an expression, `decorators` is the expression `unlockrequest(LocalizedBook, row, "title", [{ modifier: LocalizationModifier, args: ["fr"] }])` builds, which reads `fr` with `.default()` to `en`. `orderBy` and `lookup` take only names, so the expression forms sort after a `map` and look up through `joinInner`.
- **Client time** is the wall time of `await query.run()` in the bench module, in the same `ajs` process as the backend: compiling, the driver round trip and decoding. Median and p95 pool every timed run of every round; each round is a fresh `ajs` process per server, and the order of the servers rotates each round.
- **Server time and rows read** come from a separate capture pass of 5 runs per query, never from the timed runs. MySQL and MariaDB: the slow log with `long_query_time = 0` (statement time, `rows_examined`). PostgreSQL: `auto_explain` with `log_analyze` and `log_timing = off` (executor time; rows read summed over the scan nodes, filtered rows included).
- **Plans** are of the statements the module sent, as each server logged them. MySQL: `EXPLAIN FORMAT=TRADITIONAL` and `EXPLAIN ANALYZE` of the logged text, on a session given the module's own session pin. MariaDB has no `EXPLAIN ANALYZE`: it gets `EXPLAIN EXTENDED` (for the `filtered` column) and `ANALYZE`, whose table adds `r_rows` and `r_filtered`. PostgreSQL: the plan `auto_explain` logged for the module's execution, with its parameters. _Index used_ means a declared index (`titleFr` or `internalTitleFr`) appears in the plan; postgres builds them on literal `_extra` keys, which no nested read can use.
- **Correctness.** Every timed run's answer is compared with the ids the generator says it must be; ✗ marks a cell with any wrong run. The ratio divides a median of the MySQL family by the fastest **correct** postgres answer to the same question on the same table, in any form; _pg baseline_ names that form.
- **Tuning.** `innodb_buffer_pool_size = 1G` and `shared_buffers = 1GB`, so the 300k rows sit in memory on every server; `ANALYZE` on every table after seeding; every other setting is the image default. Each `ajs` run connects with the module's defaults.

## Findings

This run measures the module after the changes below; "before" is the run of 2026-11-11. Numbers marked _scratch_ time hand-written variants, which are diagnostics and not module output. MySQL scratch: a 100,000-row table seeded by SQL on a MySQL container of its own, median of 7 after a warm-up. MariaDB scratch (sections 8 to 11): the bench's own tables, seeded through the module on containers of their own, one container per version, median of 7 for filters, 5 for the per-read costs and 3 for joins and sorts, after a warm-up; MySQL 8.4 ran the same statements as the reference.

**Verdict.** Wherever a declared index can serve a question, MySQL and MariaDB now use it, in every form the question takes: key chains, the decorators' localized read, `orderBy("<index>")`, `lookup` by path and `joinInner`. Each answers in 0.4 to 0.9 ms on MySQL and 0.4 to 1.6 ms on MariaDB, against 22 to 89 ms for postgres' best correct form. Without an index, MySQL's `joinInner` hash joins like postgres, at 1.0× to 1.6× postgres instead of 23× to 41×. Every MySQL and MariaDB answer is correct. MySQL still exceeds 2× on unindexed filters (2.2× to 3.6×), on the decorators' sort after `map` (2.2× to 2.3×) and on the unindexed `lookup` (8.5× to 12×); the causes are in sections 3, 4 and 6. MariaDB 11.8 and 12.3 meet the index threshold and miss the 2× threshold on 15 of the 26 cells, from 2.6× to 136×, and the two versions agree within 8% on every one of them. The causes are in sections 8 to 11: MariaDB's JSON is text, so each read costs more the larger the document, and it has no hash join.

The causes, section by section, are in [`findings.md`](findings.md).
